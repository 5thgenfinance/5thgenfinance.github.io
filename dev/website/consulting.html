Our approach

How a conversion works

  1. Inventory. Document the current model, its inputs, outputs and known quirks.
  2. Specify. Write the specification and glossary first. AI tools guess a meaning when none is given, so definitions come before code.
  3. Convert. Build in stages. Each stage has its own tests as a gate.
  4. Reconcile. Run the old and new models side by side and explain every difference.
  5. Control and automate. Add version control, run logs, exception reports and a repeatable end-to-end process.

AI tools draft and refactor. People own the specification, review each stage and sign off on the results.

Example 1: Excel Lambda engineering

Calculation libraries inside Excel

Excel remains the fastest place to build and prove a model, and it can be built well. We use Excel’s LAMBDA function to replace long, fragile cell formulas with named, reusable functions that behave like a small calculation library.

Function libraries

Named Lambda functions for actuarial-style calculations such as survivorship from a mortality table, discounting and annuity values, reserve roll-forwards, and tax and distribution schedules.

Tested in the workbook

Each function has test cases with expected results, so a change that breaks a number shows up right away.

Documented and portable

Clear names, notes on every input and output, and a spec that lets the model move to Python later without guessing at what a formula was meant to do. In our retirement model, AI converted the Lambda library to Python with little difficulty.

Excel as the benchmark

The finished workbook becomes the check for a production system. Every number in the new system should tie back to it.

Example 2: Zero-CTO Excel to production

From Excel to a live retirement app

The problem: an adviser needs to show a client what the future looks like, with savings, investment returns, taxes, inflation, mortality, and spending all moving over decades. The question is how to turn that spreadsheet into a real web application without a developer, an architect or a software budget.

The approach was to build the model in Excel first and to treat that workbook as the source of truth. We then wrote a detailed specification and had AI tools refactor the model to Python under a staged plan. Last, we deployed the result as a web app. It is live at our Retirement Planning app.

1. Sandbox

Excel prototype with roughly 100 projection columns, a library of custom Lambda functions and unit-tested sections. It covers survivorship, expense reserves, Social Security, required distributions and federal tax.

2. Specification

Copilot reviewed the workbook for errors and deprecated functions, including off-by-one roll-forward mistakes, then produced a model specification of about 489 lines in Markdown.

3. Refactor to Python

Claude drafted a setup phase plus seven build phases. Each phase had its own tests as a stage gate.

4. Deployment

Streamlit app on GitHub test and main branches, with results matched back to the Excel model.

In this project the AI plan estimated about five weeks of work, and the build took roughly an hour and a half. That is an estimate from one project, not a guarantee. The user interface still needs more work before it is ready for less financially experienced users.

Example 3: Investment analytics agent engineering

An AI research agent that shows its work

The problem: company research written by an AI is only useful if you can see where each number came from and trust that the same method was applied each time. We built an agent-based research workflow for natural resource companies around a written methodology rather than a free-form prompt, and then improved it across two releases.

Release 1: agent from a written spec

The agent was generated from one chapter of a published valuation book and then tuned. The result is a plain-text Markdown file of about 556 lines, with a ten-factor scorecard, formula definitions, a report format and a metadata log. Data-quality checks for accuracy, hallucination and sycophancy sit at the top of every report.

Release 2.1: a governed workflow

A YAML workflow defines each step: find the technical reports, pull the latest, cross-reference the numbers, validate, compute, then score. It adds a formula library, an output format library, determinism settings, and a way to work around regulator-site throttling.

Controls and sources

The agent works from filings and technical reports first, and never from social media. Reports show an audit trail, assumptions and sensitivities. Follow-up questions let the user correct inputs and recast the report.

Tested across platforms

We ran the same agent on several AI platforms and compared the results with published reference figures. We recorded where results differed and why, and about 100 hours of testing went into the second release.

Known limits are stated openly. Very large filings can exceed a model’s context window and understate resource totals, so key inputs such as resources and share counts must be checked. Our current methodology guide is versioned, with a dated revision note for each change.

The same pattern applies to any investment analytics process: write the method down, make the agent follow it, require sources, test the assumptions and keep a version history. The research is general information and is not investment advice. The methodology is our own application of a published framework, and the author does not endorse our analysis.
